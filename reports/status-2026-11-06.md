## How it is done

Every PR is tested before it is opened. Nothing is sent on the strength of a text change alone.

- **Inventory:** every spec in Fedora is classified from the daily spec dump. The categories are plain `%gpgverify`, more complex `%gpgverify` use, and direct `gpg`/`gpgv` calls (`scripts/classify.py`).
- **Side-by-side test:** the current spec and the converted one both run in a clean mock chroot without network access. Rawhide is always tested, and ELN too where the spec mentions RHEL.
  - Wrappers log every call of the verification tools, with arguments and exit code.
  - A guard makes sure the converted spec makes the same verification calls, so a check can't silently disappear.
- **`BuildRequires: gnupg2`:** dropped only after a full build without gnupg2 passes, including `%check`. Packages whose builds or tests really use gpg keep it, and the PR says why.
- **Keyrings that `sqv` rejects** (expired key, SHA-1 self-signatures, GnuPG keybox, v3 keys): a new keyring is proposed, reviewed by hand and then tested.
  - Each one comes from a source anyone can check: upstream's own key URL, a keyserver lookup by fingerprint, or a conversion of upstream's KEYS file.
  - The exact commands go into the spec comment above the keyring's `Source` line, and into a separate first commit.
- Release is bumped with a changelog entry where the spec doesn't use `%autochangelog`. Changes go to rawhide only; other branches are up to the maintainer.

The scripts and all PR texts are in this repository.

## What is left (150) and why

| | Packages | Why |
|---|---|---|
| Signature fails with `sqv` and needs upstream or maintainer action | 117 | See below. A PR cannot fix these. |
| PR ready, held back | 19 | 7 are being opened now: bind, python-gnocchiclient, and five packages that need gpg in their build. 10 fail to build in rawhide even without our change. 2 (fedrq, python-oslo-config) have another open PR touching the same lines. |
| Keyring update being tested | 12 | 8 keyring format cases (e2fsprogs, tor, gnucobol, libextractor, httpd, ant-antunit, apache-commons-net, apache-commons-text) are approved and in testing. The rest wait on a decision. |
| Other | 2 | tinygo can't install its build dependencies; one package isn't tested yet. |

What blocks the 117 signature failures:

| Cause | Packages | Who has to act |
|---|---|---|
| The upstream key's self-signatures use SHA-1, and no newer copy exists | 51 | Upstream re-signs its key, backdated so older releases still verify ([how](https://www.redhat.com/en/blog/updating-gpg-keys-for-fedora-and-rhel)) |
| The release signatures themselves use SHA-1 | 33 | Upstream re-signs, or the next release fixes it |
| Key too weak for the crypto policy (DSA-1024, small RSA) | 12 | Upstream moves to a new key |
| The key had expired when the release was signed | 9 | Upstream publishes the extended key |
| Old v3 signatures | 8 | Mostly inactive upstreams; the maintainer may have to drop the check |
| v3 key with a SHA-1 binding | 2 | Upstream (findutils, apache-commons-vfs) |
| A subkey binding made after the signature | 2 | Upstream |

GnuPG accepts all of these. `sqv` follows the system crypto policy and checks that the key was valid and properly bound when the release was signed.

## Next steps

1. Open the 7 ready PRs and the 8 keyring format PRs after their test.
2. File bugs for the 117 signature failures, one per package, blocking rhbz#2523619. Each bug will have the failing `sqv` call and what upstream needs to do. A small pilot batch goes first.
3. Follow up on open PRs and rebase the ones whose spec has moved.
4. Run the progress report regularly (`scripts/progress.py`).
